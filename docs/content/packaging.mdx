## Starting a package

<Stub />

- A package for a library you don't own is a folder named after the package, holding an `spn.toml`, in a repository of your own.
- `[package.upstream]` gives upstream's Git `url` and a full 40 character `commit`.
- `spn build` in that folder fetches that commit; you never copy the code.
- `version` is yours to choose, and has to be a semantic version.
- Every path resolves in the upstream checkout unless the entry says [`tree = "manifest"`](/docs/packages#trees).
- `spn path NAME` prints where the upstream checkout is, so you can read upstream's build files.
- `spn` doesn't fetch Git submodules, so code upstream keeps in submodules has to come from separate packages.

## Translating upstream's build

<Stub />

- Write one `[[lib]]` per upstream library, linked to each other with target `deps`.
- Map each upstream build option to an [option](/docs/conditions#options): a bool, or an enum for mutually exclusive backends.
- Use the option in `when` to choose sources, defines, system libraries, and dependencies.
- Upstream's own build usually exposes POSIX and GNU functions that [strict C11](/docs/packages#c-standard) hides, so define the feature-test macros.
- Declare the system libraries upstream links in `system_deps`, gated by OS.
- A macro dependents also need goes in [`[package.publish] define`](/docs/packages#publishing-defines).
- Recreate upstream's include prefix with `to`, as in `include/GLFW/*.h` with `to = "GLFW"`.
- Mark a dependency `public` when upstream's public headers include its headers.
- When upstream generates sources with Python, Perl, or its own host programs, [vendor](/docs/task#vendoring) the output.

### Generated headers

<Stub />

- To replace upstream's configure or CMake step, check in the headers it would generate.
- Add that folder to `include` with `tree = "manifest"`.
- List it first if it has to shadow an upstream header of the same name.
- The include order is the package's `include`, then the target's in the order listed, then dependencies'.
- Make one header serve every platform with `#if defined(_WIN32)` and the like, or keep a copy per platform and pick with `when`.
- If upstream's public headers include a generated header (`zconf.h`, a `version.h`), publish your copy too; otherwise the package builds and dependents fail on a missing header.

## Platform conditions

### Windows

<Stub />

- Windows has two ABIs: MinGW (`abi = "gnu"`) and MSVC (`abi = "msvc"`).
- A Linux or macOS host cross compiles to MinGW, so gating MSVC-only code on `os = "windows"` breaks that build.
- Gate MSVC-only macros, libraries, and `.asm` files on `abi`.
- Gate compiler flag syntax on `driver`, because `zig` and `clang` also target the MSVC ABI.

### Linux

<Stub />

- The default Linux build is static musl; glibc is used only when the project asks for `abi = "gnu"`.
- A package has to compile against both.
- Config headers must not assume glibc; test `__GLIBC__`.
- Build the package once with `--abi musl` and once with `--abi gnu`.

## Adapting upstream code

<Stub />

- A package can't carry patches: `[patch]` only works in the project being built.
- Adapt upstream by adding your own files with `tree = "manifest"`.
- Extra sources work.
- So does a wrapper file that `#include`s an upstream file, for example to compile it as another language.
- So do shim headers listed first on the include path.

## Examples

<Stub />

- Ship one minimal example of your own, with `tree = "manifest"`, plus upstream's.
- They are the smoke test of what you publish: they include your headers by the same path a dependent does.
- An example links your libraries only if it lists them in `deps`.
- They build into `example/` in the build directory, and are never built for dependents.
- The package's `include` applies to examples too, so it can hide a header you forgot to publish; keep upstream's internal include directories on the `[[lib]]`.
- A C++ example needs its own `cxx` table.

## Checking the package

<Stub />

- `spn build` in the package's folder builds its libraries and examples, and `spn test` runs any tests you wired up.
- Cross compile to exercise other platforms' `when` branches from one machine, as in `spn build --target x86_64-windows-gnu`.
- `[profile]` and `[config]` in the package apply only to these local builds; dependents get your option defaults.
- The package's own build doesn't show what a dependent sees, so try it from a separate project.
- A path dependency on the package's folder works, and still fetches upstream.
- So does declaring your repository of manifests as a [directory index](/docs/indexes#directory-indexes).

## Publishing

<Stub />

- Run [`spn publish`](/docs/indexes#spn-publish) from the package's folder in your repository of manifests.
- The release records upstream's URL and commit as the source, and your repository, commit, and folder as the manifest.
- Every `tree = "manifest"` file has to be committed and pushed, because that commit is what dependents fetch.
- Path dependencies have to be swapped for versions first.
- Dependents fetch both repositories.
